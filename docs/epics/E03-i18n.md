# E03 · Internationalization (EN / LT)

**Goal:** The whole UI is available in English and Lithuanian, with locale-aware dates, numbers and plurals.
**Milestone:** M1 · Walking skeleton
**Depends on:** E01

---

### E03-T01 · next-intl setup & locale routing — `M`
**Why:** All features need a translation mechanism from day one; adding it later means rewriting every screen.

**Scope**
- Install `next-intl`; routes under `app/[locale]/…` with locales `en` and `lt`, default `lt`.
- Middleware that combines next-intl locale detection with Clerk's auth middleware (one `middleware.ts`).
- Locale chosen in this order: URL → `NEXT_LOCALE` cookie → saved profile locale → `Accept-Language` → `lt`.
- `messages/en.json` and `messages/lt.json` with namespaces per feature (`common`, `nav`, `auth`, `buddies`, `sessions`, `exercises`, `logging`, `progress`, `settings`, `errors`).
- TypeScript type-safe message keys (`global.d.ts` augmentation).
- `<html lang>` set to the active locale; localized `<title>` and meta description.

**Out of scope:** Language switcher UI (E03-T02); formatting helpers (E03-T03).

**Done (E03-T01):** `next-intl` 4.14.9 with `src/proxy.ts` (Next.js 16 renamed `middleware.ts` to `proxy.ts`; the next-intl handler sits in a `proxy()` function that Clerk's `clerkMiddleware` wraps in E04-T01, see the `TODO(E04-T01)` there). Routing config in `src/lib/i18n/routing.ts` (locales `lt` / `en`, default `lt`, prefix always shown, `NEXT_LOCALE` cookie kept for a year); request config in `src/lib/i18n/request.ts`, which reads the locale from the `[locale]` **root param** (`next/root-params`) because next-intl deprecated `setRequestLocale` in its favor; pages stay statically rendered and no longer take `params` for the locale. `app/[locale]/layout.tsx` is now a root layout (`<html lang>`, localized title template and meta description, `NextIntlClientProvider`); the unlocalized `/dev` and `/debug` pages moved into `app/(developer-tools)/` with their own English root layout; both share `app/root-document.tsx`. Unknown paths under a locale render the localized `[locale]/not-found.tsx` through `[locale]/[...unknownPath]`. Message keys are type-checked through the `AppConfig` augmentation in `src/global.d.ts` (`src/lib/i18n/__typetests__/message-keys.typetest.tsx`). New namespaces `auth`, `exercises`, `logging` (and `landing`) hold a minimal first set of strings. The interim `use-translations.ts` / `locale-param.ts` helpers are gone. `ThemeToggle` and `NumberStepper` (default locale) use next-intl; `UI_LABELS` stays English until E03-T03 (it needs plurals); `global-error.tsx` stays English (`TODO(E03)`: no provider above it). Deviations: the "saved profile locale" step is a `TODO(E04-T04)` in the proxy (the cookie carries it once E03-T02 / E04-T04 write it), and "protected routes still require sign-in under both locales" waits for Clerk (E04-T01). An unknown first segment is redirected to a locale first (`/de/dashboard` → `/lt/de/dashboard`, then 404).

**Acceptance criteria**
- [ ] Opening `/` with a Lithuanian browser redirects to `/lt`; with an English browser to `/en`; otherwise to `/lt`.
- [ ] Server Components (`getTranslations`) and client components (`useTranslations`) both render translated text.
- [ ] Using a key that doesn't exist fails `typecheck`.
- [ ] `<html lang>` is `lt` or `en` to match the URL.
- [x] Protected routes still require sign-in under both locales. (E04-T01: `/lt/…` and `/en/…` sections redirect to `/{locale}/sign-in`; `tests/e2e/sign-in.spec.ts`, `src/proxy*.test.ts`.)

**Depends on:** E01-T01

### E03-T02 · Language switcher & persistence — `S`
**Why:** Users must be able to change language at any time, and their choice should follow them across devices.

**Scope**
- `LanguageSwitcher` (LT / EN, shown with native names "Lietuvių" / "English") in the avatar menu and on the landing page.
- Switching replaces the locale in the current URL, keeping path and query params.
- Saves to the `NEXT_LOCALE` cookie; when signed in, also updates `profiles.locale` via Server Action.
- On sign-in, if `profiles.locale` differs from the URL, redirect to the saved locale.

**Out of scope:** Translating user-created content.

**Already in place (E03-T01):** the avatar menu's language radio items (`AccountMenu`) switch with `router.replace(getLocalizedPathname(pathname, locale))` and drop the query string (`TODO(E03-T02)`). next-intl's locale-aware navigation (`createNavigation(routing)` from `next-intl/navigation`, giving `useRouter().replace(pathname, { locale })`, `usePathname()` without the locale, `Link`) is not set up yet; create it as `src/lib/i18n/navigation.ts` from `routing` and use it for the switcher (it keeps the path; pass the current `useSearchParams()` to keep the query). The proxy only rewrites `NEXT_LOCALE` on document requests (`Sec-Fetch-Dest: document`), so a soft-navigation switch must set the cookie on the client (next-intl's `useRouter` does) or in the Server Action; name and max age are `LOCALE_COOKIE_NAME` / `LOCALE_COOKIE_MAX_AGE_SECONDS` in `src/lib/i18n/locales.ts`. The landing page (`app/[locale]/(public)/page.tsx`) has a comment where the switcher goes. Clerk's `localization` is E04-T01's.

**Done (E03-T02):** `src/lib/i18n/navigation.ts` exports next-intl's `usePathname` / `useRouter` (`createNavigation(routing)`). `useLocaleSwitch({ onLocaleChange })` (`src/components/common/language/`) opens the same path and query in the picked locale with `useRouter().replace(path, { locale })`, which also writes `NEXT_LOCALE` in the browser (same name, one-year max age, `SameSite=Lax`, from `routing`); picking the current locale does nothing. The query is read from `window.location.search` when switching instead of `useSearchParams()`, so every page stays fully prerendered without a Suspense boundary (the hash is dropped). `LanguageSwitcher` (a `SegmentedControl`, native names with `lang`, current language checked in the server HTML) is on the landing page above the theme toggle; `AccountMenu`'s Language radio items use the same hook, and `getLocalizedPathname()` is gone. `SegmentedControl` options take a `lang`. Tests: `language-switcher.test.tsx`, `account-menu.test.tsx`, `tests/e2e/language-switcher.spec.ts` (keyboard, path + query, cookie, reload, `/` follows the cookie against `Accept-Language`); unit tests that render the avatar menu now mock `next/navigation` partially (`stubAppRouterAt()` in `tests/helpers/`). **Deferred to E04** (E04 isn't built yet): saving to `profiles.locale` via a Server Action (E04-T04 passes it as `onLocaleChange`; `TODO(E04-T04)` in `AccountMenu`), the sign-in redirect to the saved locale (E04-T04, `TODO(E04-T04)` in `src/proxy.ts`), so "switch on phone, sign in on desktop opens EN" is not met yet; and Clerk components following the language (E04-T01, `TODO(E04-T01)` in `app/[locale]/layout.tsx`: since switching changes that layout's `locale` param, a `<ClerkProvider localization>` set from it follows automatically).

**Acceptance criteria**
- [x] Switching on `/lt/sessions/123?tab=x` leads to `/en/sessions/123?tab=x`.
- [ ] After switching to EN on phone, signing in on desktop opens the app in EN.
- [x] Switching is keyboard accessible and the current language is indicated.
- [ ] Clerk components (sign-in, user menu) switch language too. (E04-T01: `<ClerkProvider localization>` follows the `[locale]` param and the avatar menu is translated; the e2e checks are in `tests/e2e/sign-in.spec.ts`, gated on Clerk keys and not run yet.)

**Depends on:** E03-T01, E04-T04

### E03-T03 · Formatting helpers — `S`
**Why:** Dates, numbers and plurals look different in Lithuanian and English; wrong formats feel broken to users.

**Scope**
- `useFormat()` / `getFormat()` wrapping next-intl formatters with presets:
  - `weight(57.5)` → "57,5 kg" (LT) / "57.5 kg" (EN)
  - `date(d)`, `dateTime(d)`, `relative(d)` ("prieš 2 dienas" / "2 days ago")
  - `duration(minutes)` → "1 val. 15 min." / "1 h 15 min"
- ICU plural messages for common counts (sets, reps, sessions, exercises, buddies), using Lithuanian forms one / few / many / other.
- Times shown in the user's browser timezone; timezone passed from client to server via cookie for SSR consistency.

**Out of scope:** Unit conversion.

**Already in place (E03-T01):** `src/lib/i18n/request.ts` returns only `locale` and `messages`; add `timeZone` (from the timezone cookie, validated with zod, falling back to `Europe/Vilnius`), `now` if needed and shared `formats` there, so the server and `NextIntlClientProvider` (which inherits them from the request config in `app/[locale]/layout.tsx`) agree. Reading a cookie makes pages dynamic (they are static now), so consider formatting user-specific times only in client components or accept dynamic rendering for the signed-in area. `UI_LABELS` (`src/components/ui/ui-labels.ts`, `TODO(E03-T03)`) still has English strings with hand-written plurals ("1 result" / "N results", "and N more") and is the first candidate for the ICU plural messages. Vitest renders components with real messages through `renderWithIntl()` (`tests/helpers/render-with-intl.tsx`, time zone fixed to `Europe/Vilnius`). For ICU argument type checking, next-intl's `experimental.createMessagesDeclaration` plugin option can generate literal message types.

**Done (E03-T03):** `useFormat()` (client) and `getFormat({ locale? })` (server) in `src/lib/i18n/format/` return the presets as methods named as specified here (`weight`, `date`, `dateTime`, `relative`, `duration`), built on next-intl's `createFormatter` with the shared named formats `FORMATS` (`formats.ts`, also in the request config and type-checked through `AppConfig.Formats`): `weight` is kilograms with up to 2 decimals ("57,5 kg" / "57.5 kg", grouped: "1 250,5 kg"), `date` "2026 m. lapkričio 17 d." / "November 17, 2026", `dateTime` adds a 24-hour time ("… 07:30" / "November 17, 2026 at 07:30"), `relative` is next-intl's `relativeTime` in the best-fitting unit ("prieš 2 dienas" / "2 days ago"), `duration(minutes)` is composed from the `format.duration*` messages ("1 val. 15 min." / "1 h 15 min", "42 min", "2 h"; rounded, negative → 0) because `Intl.DurationFormat` is missing in Node 22 (it would differ between server and browser) and Intl's units say "1 hr" in English. Plurals: the `counts` namespace (`sets`, `reps`, `sessions`, `exercises`, `buddies`, LT `one` / `few` / `many` / `other`) and the `ui` namespace, which replaces `UI_LABELS` (`src/components/ui/ui-labels.ts` is gone): every default label of Button, Dialog, Sheet, Chip, AvatarStack, Combobox and NumberStepper is translated (`comboboxResultCount` is a plural; "and N more" needs none). **Time zone:** `TimeZoneCookieWriter` (`src/components/common/time-zone/`, in the root document) writes the browser's zone to the `TIME_ZONE` cookie (`src/lib/i18n/time-zone.ts`, one year, `SameSite=Lax`) when it's missing or different; `getFormat()` / `getRequestTimeZone()` read it, validated with `timeZoneSchema` (zod + `Intl.DateTimeFormat`, which also accepts `UTC`, unlike `Intl.supportedValuesOf`), falling back to `Europe/Vilnius`. **Static rendering kept (decision):** the request config sets `timeZone: "Europe/Vilnius"` (before, next-intl used the server's zone, UTC in Docker) and no `now`, and doesn't read the cookie, so every page is still prerendered (●); `useFormat()` renders in the provider's zone on the server and during hydration and switches to the browser's right after (`useSyncExternalStore`, no mismatch), and dynamic pages read the cookie (`getFormat()` makes the route dynamic). Trade-off: on a static page, or on the very first visit before the cookie exists, a user outside Vilnius sees the time change once after hydration (the inline-script technique from Next's "preventing flash" guide was not needed for the signed-in pages, which will be dynamic). Preview and e2e: `/dev/format` (dev only) renders every preset with `getFormat()` and with `useFormat()` in both locales; `tests/e2e/formatting.spec.ts` checks it in a New York browser with no console errors (hydration) and server = client text after the cookie is set. **Deviations:** CLDR puts Lithuanian decimals in `many`, not `other` ("1,5 serijos", genitive singular; `other` is 0 and 10–20: "10 serijų"), so the criterion below is met with `many`; English dates follow `en` (US) month–day order ("November 17, 2026"), while the mock-ups' home header shows "Tuesday, 17 November" (British order would need an `en-GB` formatting locale; not done; the weekday header is E07-T07's own format). **Deferred:** ICU argument type checking (`createMessagesDeclaration`; a missing `count` is a runtime error only), passing `now` / the cookie's zone to a provider in the signed-in layout (E04, see README → Translations), `relative()` times that keep updating (`useNow({ updateInterval })`), the NumberStepper's own formatting (same separator and 2 decimals as `weight()`, but no digit grouping because the text is editable; its `aria-valuetext` says "1250,5 kg").

**Acceptance criteria**
- [x] LT plurals render correctly: "1 serija", "2 serijos", "10 serijų", "21 serija", "1,5" (decimals use "other"). (Decimals use CLDR's `many`: "1,5 serijos"; see Deviations.)
- [x] EN plurals: "1 set", "2 sets".
- [x] Weights and dates follow the active locale in both server and client renders (no hydration mismatch warnings).
- [x] Unit tests cover all presets in both locales.

**Depends on:** E03-T01

### E03-T04 · Missing-key check in CI — `S`
**Why:** It's easy to add an English string and forget the Lithuanian one; CI should catch it.

**Scope**
- Script `npm run i18n:check` that compares the key trees of `en.json` and `lt.json` and reports keys missing in either file, empty values, and ICU syntax errors.
- Added to the CI lint job.
- Short contributor note in the docs: how to add a new string.

**Out of scope:** Machine translation.

**Already in place (E03-T01):** `src/lib/i18n/messages.test.ts` already compares the key trees (flat, two levels: namespace → key), rejects empty values and the ASCII apostrophe (ICU quoting), and checks the feature namespaces exist; `MESSAGES` (`src/lib/i18n/messages.ts`) is typed against `en.json`, so a key missing in `lt.json` already fails `typecheck`. The script can reuse that logic for clearer output (file + key path) and add ICU syntax checks; `intl-messageformat` / `@formatjs/icu-messageformat-parser` are installed as next-intl dependencies (add the parser as a direct, pinned dev dependency rather than relying on the transitive one). Since E03-T03 the messages hold ICU plurals (`counts.*`, `ui.comboboxResultCount`) and simple arguments (`format.duration*`, `ui.remove`, `ui.comboboxCreate`, `ui.numberStepper*`, `ui.hiddenAvatars`); `messages.test.ts` renders the plurals in both locales. Worth checking too: every `plural` in `lt.json` has `one`, `few`, `many` and `other`, and both files use the same argument names per key.

**Done (E03-T04):** `npm run i18n:check` (`scripts/check-i18n.mts`, run with Node's type stripping like `check:contrast`) reads every `messages/<locale>.json` in parallel (`en.json`, which `MESSAGES` is typed against, is the reference), validates each with zod (nested objects of strings, any depth; a file that is unreadable, not JSON, the wrong shape, not named after a locale `Intl` knows, or a missing `en.json` stops the run with exit code 2), then collects every problem and prints one line each as `<file>: <problem>` (plus a `::error file=…` annotation under GitHub Actions) and exits 1: a key missing in either file (every missing leaf path is listed; a message in one file that is a group in the other is reported once), an empty or whitespace-only value, an ASCII apostrophe, an ICU syntax error from `@formatjs/icu-messageformat-parser` (the parser next-intl uses; e.g. `EXPECT_ARGUMENT_CLOSING_BRACE`, `MISSING_OTHER_CLAUSE`), a `plural` / `selectordinal` (also nested inside `select` options and rich-text tags) missing a category its file's locale needs (from `Intl.PluralRules`, so EN `one`, `other` and LT `one`, `few`, `many`, `other` without a hard-coded list; extra categories and `=0`-style exact matches are allowed), and arguments (including rich-text tag names) that differ from `en.json`'s. The checks are pure functions in `scripts/i18n/` (`checkMessageCatalogs()`, `readMessageCatalogs()`); `src/lib/i18n/messages.test.ts` now runs `checkMessageCatalogs()` on `MESSAGES` instead of its own key-parity, empty-value and apostrophe tests, so `npm test` and the script can't drift. The CI **Lint, typecheck, format** job runs it as the "Check translations" step. Tests: `tests/unit/scripts/check-i18n.test.ts` (fixtures for a key only in EN / only in LT, nested groups, message vs group, empty values, unclosed plural, missing `other`, missing LT and EN plural categories, ordinals, nested plurals, mismatched arguments, apostrophe, reading and the script's output and exit codes). Contributor note: README → Design tokens and dev pages → **Adding a string**; output examples in `docs/ci.md` → Translations check. `@formatjs/icu-messageformat-parser` 3.5.18 (released 2026-09-12, the version next-intl 4.14.9 already installed, so the lockfile only hoists it) is a pinned dev dependency. Runs in about 0.25 s. **Not done (decided):** duplicate keys inside one JSON file aren't detected (`JSON.parse` keeps the last one; Prettier and review catch them), unused keys in code aren't reported, and plural categories a locale never uses (e.g. `few` in EN) aren't flagged.

**Acceptance criteria**
- [x] Adding a key only to `en.json` fails CI and the output lists the missing key path and file.
- [x] An empty string value or broken ICU syntax (e.g. unclosed `{count, plural`) fails the check.
- [x] The check runs in under 5 seconds.

**Depends on:** E03-T01, E01-T05
