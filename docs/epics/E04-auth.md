# E04 · Authentication & Profile

**Goal:** Users sign in with Google, get a profile automatically, and every DB request is authorized by RLS using their Clerk identity.
**Milestone:** M1 · Walking skeleton
**Depends on:** E01

### E04-T01 · Clerk with Google sign-in — `S`
**Why:** Google login is the only sign-in method required; it removes passwords and makes joining a friend's session quick.

**Scope**
- Clerk application (dev instance) with **Google** as the only enabled method; email/password and other providers disabled.
- `<ClerkProvider>` in the root layout with `localization` set from the active locale (`ltLT` / `enUS`) and `appearance` using design tokens.
- Sign-in page `/[locale]/sign-in` with Clerk `<SignIn />`; after sign-in redirect to `/[locale]` Home, or to the originally requested URL.
- Middleware protects every route in `(app)`; public: landing, sign-in, `/api/webhooks/*`.
- Sign out from the avatar menu.

**Out of scope:** Profile table (E04-T03).

**Already in place (E03-T01):** the one Proxy is `src/proxy.ts` (Next.js 16's name for middleware; `middleware.ts` is deprecated). It exports `proxy()`, which calls next-intl's `handleLocaleRouting`; replace that export with `clerkMiddleware(async (auth, request) => { … return handleLocaleRouting(request); })` and add Clerk's API matcher (see the `TODO(E04-T01)` there). There are two root layouts: `app/[locale]/layout.tsx` (all localized pages; put `<ClerkProvider>` there, the locale is its `params.locale` / `getLocale()`) and `app/(developer-tools)/layout.tsx` (`/dev`, `/debug`, no Clerk needed). `auth.signIn` / `auth.signOut` messages exist. **E03-T02:** the `TODO(E04-T01)` in `app/[locale]/layout.tsx` marks where `<ClerkProvider localization>` goes (`ltLT` / `enUS` from `locale`); the language switch changes that layout's `locale` param, so Clerk's components follow it — add an e2e check that `<SignIn />` and the user menu change language with the switch (E03-T02's last acceptance criterion).

**Acceptance criteria**
- [ ] Opening `/lt/sessions` while signed out redirects to sign-in, then back to `/lt/sessions` after Google login. — The redirect to `/lt/sign-in?redirect_url=…/lt/sessions` is verified (unit tests with and without Clerk, e2e without keys). The way back is Clerk's `redirect_url` handling, covered by the gated e2e `returns to the page that asked for sign-in` (a sign-in ticket completed by `<SignIn />`); not run yet: no Clerk dev keys in the agent sandbox / CI.
- [ ] Only the "Continue with Google" option is visible. — A Clerk dashboard setting (deployment.md → Clerk); checked by the gated e2e `offers only Continue with Google`, not run yet.

### E04-T02 · Clerk ↔ Supabase integration — `S`
**Why:** Supabase must know who the user is on every request, so RLS can enforce privacy in the database rather than in app code only.

**Scope**
- Add Clerk as a **third-party auth provider** in Supabase (local `config.toml`, staging, production) and activate the Supabase integration in Clerk.
- Supabase clients (E01-T03) pass `accessToken: async () => (await auth()).getToken()` on the server and `session.getToken()` in the browser.
- SQL helper `uid()` returning `auth.jwt()->>'sub'` (`stable`), used by all RLS policies.
- Local development: RLS test helper signs equivalent JWTs (E01-T04).

**Out of scope:** Profile sync (E04-T03).

**Already in place (E04-T01):** Clerk runs in the proxy for every page and API route, so `auth()` from `@clerk/nextjs/server` works in the server client (`src/lib/supabase/server.ts`: `accessToken: async () => (await auth()).getToken()`); in the browser `useClerk().session?.getToken()` / `window.Clerk.session.getToken()` is available below `ClerkAccountProvider`. `isClerkConfigured()` (`src/lib/auth/clerk-env.ts`) is false in CI's no-key jobs: keep the signed-out stub there. RLS test JWTs (`tests/helpers/supabase-auth.ts`) already carry `sub` = a Clerk-style user id; the real Clerk session token needs the Supabase integration activated in the Clerk dashboard (it adds `role: authenticated`).

**Acceptance criteria**
- [x] With a test table protected by `using (owner_id = uid())`, a signed-in user reads only their own rows. — `tests/db/rls/third-party-auth.test.ts` (test table `uid_fixture_notes`, policy `owner_id = (select uid())`), run against the local stack.
- [x] A request without a token (anonymous) gets zero rows from protected tables and cannot insert. — Same file (zero rows, insert `42501`); also a valid token without `role: authenticated` (Clerk before the Supabase integration) acts as `anon`.
- [x] A forged or expired token is rejected by Supabase. — Same file: wrong HS256 secret, an unknown RS256 key (another issuer), `alg: none` → 401 `PGRST301`; expired → 401 `PGRST303`; checked locally with the stack's signing secret. Rejecting a real Clerk token from another instance on staging/production needs those projects (go-live check below).
- [ ] Works the same in local, preview and production environments. — Same code and migration everywhere; locally verified with the DB tests' tokens (equivalent claims). Not verified with real Clerk tokens: that needs the dashboard steps (Clerk Supabase integration, Supabase third-party auth; docs/deployment.md → Supabase Cloud step 4, Clerk step 2) and the go-live check in docs/deployment.md (item 1), and locally a reachable Clerk dev instance (README → Authentication). No Clerk instance or network to it from the sandbox this was built in.

**Done (E04-T02):**
- **Migration** `20261123213000_add_uid_function.sql`: `public.uid()` → `auth.jwt()->>'sub'` (`text`, `stable`, `security invoker`, `search_path = ''`, `create or replace`, so re-running is harmless); `null` without a token. Generated types now list `uid` under `Functions` (`supabase.rpc("uid")`). Policies use it as `(select uid())` (evaluated once per statement), owner columns default to `uid()`. `auth.uid()` must not be used (casts to uuid). `sample_notes` keeps its inline `auth.jwt()->>'sub'` (equivalent; it is dropped in E04-T03).
- **Server client** (`src/lib/supabase/server.ts`): the default `accessToken` is `(await auth()).getToken()`; without Clerk keys (`isClerkConfigured()` false: CI, Docker) it returns `null` without calling Clerk, so requests are `anon` (fail closed).
- **Browser client:** `Account` (`useAccount()`) gained `getToken()` — `ClerkAccountProvider` reads `clerk.session?.getToken()` on every call, so a token is never served after sign-out. `useSupabaseBrowserClient()` (`src/components/common/auth/use-supabase-browser-client.ts`) passes it to `createBrowserClient()`, whose tab singleton now uses the **latest** caller's token provider (was: the first caller's options), so signing in or out switches every query and channel. No account (Clerk loading, signed out, no keys) = `anon`.
- **Local stack** (`supabase/config.toml` `[auth.third_party.clerk]`): `domain = "env(CLERK_FRONTEND_API_DOMAIN)"`, `enabled = false` by default and switched on with `SUPABASE_AUTH_THIRD_PARTY_CLERK_ENABLED=true` (the CLI's env override; both in `.env.local`, which the CLI reads). Default off because with it on `supabase start` fetches the Clerk instance's JWKS and fails without network or a domain (CI, fresh checkouts); the local HS256 secret stays valid, so the DB tests run either way. `.env.example`, README → Authentication.
- **Staging / production:** Supabase dashboard → Third-Party Auth → Clerk, and Clerk → Supabase integration, in docs/deployment.md (Supabase Cloud step 4, Clerk step 2) with a go-live check (item 1: `rpc/uid` with a real token returns the Clerk id; a tampered one 401). Not done here (no dashboard access).
- **Tests.** DB: `tests/db/rls/third-party-auth.test.ts` (`uid()` = `sub`, `null` for anon, `stable`; the test table: own rows only, owner default, insert for someone else `42501`, anon zero rows / no insert, token without role = anon; forged / other-key / `alg: none` / expired → 401). Helpers: `createClientWithToken(token)` and an explicit signed-out `createAnonClient()` in `tests/helpers/supabase-auth.ts`, `queryAsSuperuser()` in `tests/helpers/db.ts`. Unit: `server.test.ts` (Clerk token sent; anon key when signed out; Clerk not called without keys; explicit provider wins), `client.test.ts` (signed out by default; one client follows the latest session), `use-supabase-browser-client.test.tsx`, `clerk-account-provider.test.tsx` (`getToken` reads the current session; `null` after it's gone); `tests/helpers/supabase-fetch.ts` (`stubSupabaseFetch()`: captures the `Authorization` header without network), the Clerk mock's `useClerk()` now has `session.getToken` (`MOCK_SESSION_TOKEN`) once `mockSignedInUser()` is called.
- **Deviations:** the test table is created by the DB test itself, not by a migration, so it never reaches staging/production. The criterion's `using (owner_id = uid())` is written `(select uid())` (same result, the RLS performance pattern). Local Clerk is opt-in rather than always on (see above). No UI change.

### E04-T03 · Profiles table & sync — `M`
**Why:** Other users need to see a name and avatar (buddies, sessions), and the app needs to store preferences such as language and theme.

**Scope**
- Migration for `profiles` (see [data-model.md](../data-model.md#profiles)) with RLS: users can read and update their own profile; visibility to buddies and co-participants is added in E05-T01 / E07-T01.
- Users may update only `locale` and `theme`; `display_name`, `email`, `avatar_url` come from Clerk.
- Route `/api/webhooks/clerk` handling `user.created`, `user.updated`, `user.deleted`, verified with the Svix signature, writing via the service-role client.
- Fallback: on the first authenticated request, if no profile exists, create it from Clerk's `currentUser()`.
- Webhook is idempotent (repeated events give the same result).

**Out of scope:** Full GDPR deletion of related data (E10-T05).

**Already in place (E04-T01):** `/api/webhooks/*` is public in `isProtectedPath()` (`src/lib/auth/auth-routes.ts`) and still passes through `clerkMiddleware` (signed out, no locale step), so the route only has to verify the Svix signature (`verifyWebhook` from `@clerk/nextjs/webhooks`, `CLERK_WEBHOOK_SIGNING_SECRET`). `currentUser()` from `@clerk/nextjs/server` works in Server Components for the first-request fallback; the avatar menu already shows Clerk's name, email and photo (`ClerkAccountProvider`), which the profile could replace or feed.

**Already in place (E04-T02):** `uid()` for the policies (`using (id = (select uid()))`, `id text primary key` = the Clerk user id; the webhook writes it from `data.id`). `createServerClient()` already acts as the signed-in user (Clerk token), so the first-request fallback can read the user's own profile through RLS and insert it with the service-role client (`createAdminClient()`) or through an own-row insert policy. RLS tests: copy `tests/db/rls/sample-notes.test.ts` (`createUser()`, `createClientAs(user)`, `createAnonClient()`, `createServiceClient()` to arrange data); drop `sample_notes`, its type test and its RLS test in a new migration as planned (data-model.md → Dev/test fixtures). Column-level "only `locale` and `theme`" can be enforced with `revoke update … ; grant update (locale, theme) on public.profiles to authenticated`, tested with `42501`.

**Acceptance criteria**
- [ ] A brand-new Google user has a `profiles` row within 5 seconds of first sign-in, even if the webhook is delayed. — Implemented: the first signed-in page (the `(app)` layout's `EnsureProfile`, which renders when the user lands in the app after sign-in) creates the row from `currentUser()` if the webhook hasn't. `tests/db/profiles/get-current-profile.test.ts` checks it against the local database with Clerk mocked (row created and returned, well under 5 s; an existing or newer webhook row is kept; deleted users aren't revived). Not verified with a real Google sign-in: no Clerk keys in the agent sandbox / CI; go-live check in docs/deployment.md (item 10).
- [x] Changing the Google account name/photo updates `display_name`/`avatar_url` after the next `user.updated` event. — `tests/db/profiles/clerk-webhook.test.ts` (signed `user.updated` → new name and photo, photo removed → `null`, `locale` / `theme` / `invite_code` kept; an older event arriving later is ignored). That Clerk sends `user.updated` after a Google profile change (Clerk refreshes it on the next Google sign-in) is Clerk's behaviour, checked in go-live item 10.
- [x] A request with a missing or invalid Svix signature returns 401 and changes nothing. — `src/app/api/webhooks/clerk/route.test.ts` (no headers, another secret, body changed after signing, signature older than 5 minutes → 401, no write) and the DB test (wrong secret → 401, no row).
- [x] Replaying the same webhook event twice doesn't create duplicates or errors. — DB test: the same signed delivery twice → `200 synced`, then `200 ignored_outdated`, one unchanged row (`updated_at` too); `user.deleted` twice → `200` both times.
- [x] RLS tests: user A cannot read or update user B's profile (before they are buddies). — `tests/db/rls/profiles.test.ts`.
- [x] A user cannot change their own `email` or `display_name` through the API. — Same file: updating `email`, `display_name`, `avatar_url`, `invite_code` or `id` of the own row → `42501` (column grant: only `locale`, `theme`), row unchanged; no insert / delete; the sync functions and `deleted_users` are not reachable for `authenticated` / `anon`.

**Done (E04-T03):**
- **Migration** `20261123213711_add_profiles.sql` (idempotent): drops the `sample_notes` fixture; `public.profiles` as in [data-model.md](../data-model.md#profiles) plus `clerk_updated_at` (see deviations), check constraints for `locale` (`lt`/`en`), `theme` (`light`/`dark`/`system`), canonical email (trimmed + lowercase), non-empty name, `https://` avatar; `invite_code` default 16 base64url characters from 96 random bits (`pgcrypto`); `updated_at` trigger via a reusable `set_updated_at()`. RLS: `select` and `update` of the own row (`id = (select uid())`), `revoke all` from `anon` / `authenticated`, then `grant select` and `grant update (locale, theme)` to `authenticated`; no insert / delete for users. `public.deleted_users` (id + time, service role only) remembers deleted Clerk ids. Two service-role-only functions (execute revoked from `public`, `anon`, `authenticated`): `sync_profile_from_clerk(…)` (upsert of the Clerk columns only if newer than the stored `clerk_updated_at` and not deleted; returns `synced` / `ignored_outdated` / `ignored_deleted`) and `delete_profile_from_clerk(id)` (tombstone + delete). Types regenerated (`src/types/database.ts`).
- **Webhook** `POST /api/webhooks/clerk` (`src/app/api/webhooks/clerk/route.ts`): `CLERK_WEBHOOK_SIGNING_SECRET` validated with zod (`whsec_…`; missing → throws → 500, Clerk retries), `verifyWebhook()` from `@clerk/nextjs/webhooks` (Svix headers, HMAC, 5-minute timestamp tolerance) → 401 `{"error":"invalid_signature"}` on any failure; the verified event is parsed with zod (`clerkUserEventSchema`, `src/lib/profiles/clerk-webhook.ts`), other event types / unexpected payloads → `200 {"status":"ignored_unsupported"}` with a warning that names only the type (no personal data in logs); `handleClerkUserEvent()` → `200 {"status": "synced" | "ignored_outdated" | "ignored_deleted" | "deleted" | "ignored_no_email"}`; database errors throw → 500 → retried. Mapping (`buildProfileSyncInput()`): name = "first last", else username, else the email's local part; primary email lowercased; photo only when `has_image` and `https`, else `null`.
- **Out-of-order events:** newer data wins by Clerk's `updated_at` (stored as `clerk_updated_at`), so a late `user.created` after `user.updated`, an older `user.updated`, or a replay change nothing; after `user.deleted` the id is in `deleted_users`, so a retried `user.created` / `user.updated` doesn't bring the profile (and the email) back.
- **Fallback:** `getCurrentProfile()` (`src/lib/profiles/get-current-profile.ts`, React `cache()` per request): `null` without Clerk keys (no Clerk call) or signed out; reads the own row through RLS (`createServerClient()`); if missing, `currentUser()` → `sync_profile_from_clerk()` (service role; the same newer-wins rule, so it never overwrites webhook data) → reads again. It runs in `EnsureProfile` (`src/components/common/auth/ensure-profile.tsx`), streamed in a `<Suspense fallback={null}>` in `app/[locale]/(app)/layout.tsx`: the page doesn't wait for it, errors are reported to Sentry instead of breaking the signed-in area (Next.js signals are rethrown with `unstable_rethrow`), and `connection()` keeps the signed-in pages out of prerendering (they are now `ƒ` dynamic in `next build`; before they were SSG, which would never have run the fallback).
- **Tests.** DB: `tests/db/rls/profiles.test.ts` (own row read/update, other user's row invisible and not updatable, Clerk columns / id / invite code `42501`, unsupported locale/theme `23514`, every `LOCALES` / `THEME_PREFERENCES` value accepted, no insert/delete, anon nothing, functions and `deleted_users` closed to users, invite code format and uniqueness, canonical email and unique email), `tests/db/profiles/clerk-webhook.test.ts` (real route + signature + SQL: create, 401 no write, replay, update keeps preferences, photo removed, older update ignored, late `user.created` ignored, delete + replayed delete, no resurrection), `tests/db/profiles/get-current-profile.test.ts` (fallback; Clerk server mocked). Unit: `route.test.ts` (401 cases, deleted, ignored types, no email, missing secret, DB failure), `build-profile-sync-input.test.ts`, `clerk-webhook.test.ts`, `get-current-profile.test.ts` (no keys / signed out), `ensure-profile.test.tsx`. Helpers: `createProfile()` factory, `tests/helpers/clerk-webhook.ts` (Svix-style signing with `node:crypto` — no `svix` dependency added; the real `standardwebhooks` verifier checks it). The `sample_notes` RLS test is gone; the type test and the unit tests' example queries use `profiles`.
- **Deviations:** extra column `profiles.clerk_updated_at` and the table `deleted_users` (not in data-model.md before; now documented) for out-of-order events; inserts and Clerk-column updates go through SQL functions rather than a plain upsert (PostgREST can't express "update only if newer"). The `sample_notes` type test was rewritten for `profiles` instead of deleted (it still guards the typed client). The fallback runs in the `(app)` layout (first signed-in page), not in the proxy (no database round trip on every request). No UI change; the avatar menu still reads Clerk's name and photo (`useAccount()`), which are the same data.

**Already in place (E04-T03) for later tasks:** read the signed-in user's profile on the server with `await getCurrentProfile()` (`@/lib/profiles/get-current-profile`; `Profile | null`, request-cached, safe to call from any Server Component, Server Action or Route Handler under `(app)`; never inside `"use cache"`). `locale` and `theme` columns are typed `string`: parse them with `localeSchema` / `themePreferenceSchema` before use. Users can only `update` `locale` / `theme` of their own row (other columns → `42501`). Profile writes from Clerk go through `syncProfileFromClerk()` / `deleteProfileFromClerk()` (`@/lib/profiles/sync-profile`, service role). DB tests: `createProfile(user, overrides)` from `tests/factories`. ### E04-T04 · Settings page — `S`
**Why:** Users need one place to see their account and set language and theme preferences that follow them across devices.

**Scope**
- `/[locale]/settings` with sections:
  - **Account:** avatar, name, email (read-only, "Managed by Google"), link to Clerk's account management.
  - **Preferences:** language (LT/EN), theme (light/dark/system).
  - **Sign out.**
  - Placeholder for "Export data" and "Delete account" (filled in E10-T05).
- Saving preferences via a Server Action updating `profiles`; changes apply immediately.
